## 3. Проектирование БД

```
authors 1 ────── N books N ────── 1 genres
                    │ 1
                    │
                    │ N
                 loans            <- промежуточная таблица связи N:M
                    │ N
                    │
                    │ 1
                 readers
```

Связи:

- `authors 1:N books` — у автора много книг, книга принадлежит одному автору;
- `genres 1:N books` — у жанра много книг;
- `books N:M readers` — через промежуточную таблицу `loans` (книга выдаётся многим читателям,
  читатель берёт много книг); в `loans` хранятся атрибуты связи: `loan_date`, `due_date`, `return_date`;
- `books 1:N loans`, `readers 1:N loans` — те же связи со стороны выдачи.

Таблицы: `authors`, `genres`, `readers`, `books`, `loans` (5 таблиц, 4 внешних ключа).

### Нормализация

- **1НФ**: все атрибуты атомарны, повторяющихся групп нет — жанр и автор вынесены
  в отдельные таблицы, а не перечислены строками в `books`.
- **2НФ**: неключевые поля зависят от полного первичного ключа; в `loans` суррогатный
  `id`, а составной уникальный ключ `(book_id, reader_id, loan_date)` не имеет частичных зависимостей.
- **3НФ**: транзитивных зависимостей нет — имя автора хранится в `authors`, а не в `books`;
  название жанра — в `genres`; изменение названия жанра не затрагивает таблицу книг.

Ограничения целостности: `NOT NULL` для обязательных полей, `UNIQUE` для `authors.full_name`,
`genres.name`, `readers.email`, `CHECK` для года, цены, количества экземпляров
(`copies_available BETWEEN 0 AND copies_total`), корректности e-mail и дат выдачи.

## 4. SQL

Файл `queries.sql` содержит 16 запросов; ниже — соответствие требованиям методички.

| № | Требование | Что делает запрос |
|---|---|---|
| 1 | `SELECT` | все книги с расшифровкой автора и жанра |
| 2 | `WHERE` | книги дешевле 600 ₽, которые есть в наличии |
| 3 | `ORDER BY` | сортировка по году издания |
| 4 | `JOIN` | читатель + книга + даты выдачи (3 таблицы) |
| 5 | `LEFT JOIN` | все книги и число выдач, включая книги без выдач |
| 6 | `GROUP BY` | число книг и средний год издания по авторам |
| 7 | `HAVING` | жанры, где больше двух книг |
| 8 | `COUNT` | число книг, доступных экземпляров, активных выдач |
| 9 | `AVG` / `SUM` | средняя цена книги и стоимость фонда |
| 10 | `INSERT` | добавление книги |
| 11 | `UPDATE` | изменение цены |
| 12 | `DELETE` | удаление добавленной книги |
| 13 | подзапрос | книги дороже средней цены фонда |
| 14 | несколько условий | активные просроченные выдачи за период |
| 15 | связь нескольких таблиц | топ читателей по числу взятых книг |
| 16 | агрегаты + `HAVING` | жанры со средней ценой выше 500 ₽ |

Все запросы приложения выполняются **только с параметрами**:

```python
cursor.execute(f"{BOOK_SELECT} WHERE b.id = ?", (book_id,))
```

Динамически подставляются лишь имена столбцов сортировки — из белого списка
`SORT_COLUMNS`, значения всегда передаются параметрами.

**SQL injection** — приём, когда ввод пользователя склеивается с SQL-кодом и меняет его смысл
(`' OR '1'='1`). Параметризованные запросы отправляют значения отдельно от текста запроса,
поэтому ввод трактуется как данные, а не как SQL. Плюс `CHECK`-ограничения и валидация в Service
не дают записать заведомо некорректные значения.

## 5. Индексы

| Индекс | Поле | Для чего |
|---|---|---|
| `idx_books_title` | `books(title)` | поиск книги по названию, `ORDER BY title` |
| `idx_books_author` | `books(author_id)` | `JOIN authors` и фильтр по автору |
| `idx_loans_reader` | `loans(reader_id, return_date)` | активные выдачи читателя (`GET /readers/{id}/loans`) |
| `idx_loans_book` | `loans(book_id, return_date)` | проверка выдач книги перед удалением/выдачей |

Индекс ускоряет чтение, но замедляет `INSERT`/`UPDATE`/`DELETE` и занимает место, поэтому
его не создают на каждом столбце: для полей с малой мощностью (`available`, `year`) выгода
минимальна, а на редко используемых в фильтрах полях индекс только добавляет накладные расходы.

Проверка плана запроса (тест `test_indexes_exist_and_are_used`):

```sql
EXPLAIN QUERY PLAN SELECT id FROM books WHERE title = 'Война и мир';
-- SEARCH books USING INDEX idx_books_title (title=?)
```

## 6. Транзакция

Бизнес-операция «выдать книгу» (`BookService.borrow_book`) обязана быть атомарной:

```
BEGIN
  SELECT книга (проверка существования)
  SELECT читатель (проверка существования)
  UPDATE books SET copies_available = copies_available - 1
         WHERE id = ? AND copies_available > 0
  INSERT INTO loans (...)
COMMIT      -- при любой ошибке ROLLBACK
```

Возврат книги (`return_book`) — тоже транзакция: `UPDATE loans SET return_date` +
`UPDATE books SET copies_available = copies_available + 1`.

Если вставка выдачи падает, `Database.transaction()` выполняет `ROLLBACK`: остаток
экземпляров не уменьшается и «полувыданной» книги не остаётся. Это проверяют тесты
`test_borrow_rolls_back_when_loan_insert_fails` и `test_borrow_book_without_copies_raises_and_keeps_state`.

ACID: **Atomicity** — выдача целиком или никак; **Consistency** — `CHECK`
`copies_available BETWEEN 0 AND copies_total` и FK не дают нарушить состояние;
**Isolation** — условный `UPDATE ... WHERE copies_available > 0` защищает от гонки;
**Durability** — после `COMMIT` изменения сохранены в файле БД.

## 8. NoSQL: Redis для истории поиска

Выбрана **Redis**, потому что кэшируемые данные варианта (история поиска) — это быстрые
key-value записи с естественным TTL: список последних запросов и счётчики частоты.
Документная модель MongoDB здесь избыточна: структура плоская и не меняется.

| Ключ | Тип | Содержимое | TTL |
|---|---|---|---|
| `library:search:history` | строка (JSON-список) | последние 10 поисковых запросов | 3600 c |
| `library:search:count:{query}` | счётчик | сколько раз искали запрос | 86400 c |
| `library:book:{id}` | строка (JSON) | кэш карточки книги | 60 c |

Использованы все пять операций из задания: `SET` (кэш книги), `GET` (чтение кэша),
`DELETE` (инвалидация), `EXPIRE` (TTL истории и счётчиков), `INCR` (счётчик частоты запросов).

**Cache-aside** (`GET /books/{id}`):

```
запрос → GET library:book:<id>
           ├── есть → вернуть из кэша (без обращения к БД)
           └── нет  → SELECT из SQLite → SET library:book:<id> EX 60 → ответ
```

**TTL** нужен, потому что цена и наличие меняются: бесконечно кэшировать изменяемые данные
нельзя — клиент получит устаревшую цену. **Cache invalidation**: после `POST`, `PUT`, `PATCH`,
`DELETE` и после выдачи/возврата книги ключ `library:book:{id}` удаляется, поэтому следующий
`GET` читает свежие данные из БД.

Если Redis недоступен, `create_cache()` возвращает `InMemoryTTLCache` с тем же интерфейсом —
приложение и тесты работают без внешнего сервера (важно для проверки работы преподавателем).

## 9. CDN

Внешний CDN не использовался — по п. 37 методички допускается локальная имитация:
`cdn_server.py` поднимает два HTTP-сервера на одном наборе файлов.

| Роль | URL | Cache-Control | Поведение |
|---|---|---|---|
| origin | `http://127.0.0.1:8001/...` | `no-store` | каждый запрос читает файл с диска |
| CDN edge | `http://127.0.0.1:8002/...` | `public, max-age=60` | первый запрос `MISS`, далее `HIT` + `Age` |

Ресурсы: `images/cover-1.jpg` (161 897 Б), `images/cover-2.jpg`, `images/cover-3.jpg`,
`css/style.css`, `js/app.js`. Обложки книг в БД ссылаются на `cover_url`
(`/static/images/cover-1.jpg` и т. д.).

Результат `python cdn_experiment.py` (полностью — в `cdn_report.md`):

| Источник | Ресурс | Попытка | Код | Размер, байт | Время, мс | Cache-Control | Age | X-Cache |
|---|---|---|---|---|---|---|---|---|
| origin | images/cover-1.jpg | 1 | 200 | 161897 | 16.00 | no-store | — | BYPASS |
| cdn | images/cover-1.jpg | 1 | 200 | 161897 | 1.69 | public, max-age=60 | 0 | MISS |
| origin | images/cover-1.jpg | 2 | 200 | 161897 | 2.28 | no-store | — | BYPASS |
| cdn | images/cover-1.jpg | 2 | 200 | 161897 | 1.37 | public, max-age=60 | 1 | HIT |
| cdn | css/style.css | 1 / 2 | 200 | 1499 | 1.65 / 1.34 | public, max-age=60 | 0 / 1 | MISS / HIT |
| cdn | js/app.js | 1 / 2 | 200 | 2775 | 1.68 / 1.73 | public, max-age=60 | 0 / 1 | MISS / HIT |

Выводы: CDN отдаёт повторный запрос из кэша edge-узла (`X-Cache: HIT`, растёт `Age`),
origin каждый раз читает файл (`no-store`, `X-Cache: BYPASS`). `max-age=60` означает,
что 60 секунд ресурс считается свежим; после этого edge перезапрашивает origin.
Для обложек это допустимо (файлы меняются редко), а цену и наличие отдавать через CDN нельзя —
они меняются и должны идти из БД.

## 10. Сравнение технологий

| Характеристика | SQLite/PostgreSQL | MongoDB | Redis | CDN |
|---|---|---|---|---|
| Основное назначение | основное хранилище, источник истины | документы с гибкой схемой | кэш, сессии, счётчики | доставка статики |
| Структура | таблицы, строки, столбцы | коллекции документов (BSON/JSON) | key-value | файлы по URL |
| Хранение | файл (SQLite) / сервер (PostgreSQL) | сервер, документы | память (+ persistence) | edge-серверы |
| Запросы | SQL, JOIN, агрегаты | `find`, aggregation pipeline | `GET/SET/INCR/EXPIRE` | HTTP GET |
| Транзакции | полные, ACID | много-документные (с ограничениями) | ограниченные, атомарны команды | нет |
| Кэширование | нет встроенного | нет встроенного | основная функция, TTL | кэш HTTP (`Cache-Control`, `Age`) |
| Масштабирование | реплики, шардирование | шардирование из коробки | кластер, репликация | глобально, много узлов |
| Типичные данные | книги, читатели, выдачи, цены | профили, каталоги с разной структурой | история поиска, счётчики, кэш карточек | обложки, CSS, JS, видео |
| Когда использовать | строгая схема, связи, отчётность | меняющаяся схема, вложенность | быстрый доступ к временным данным | публичный статический контент |

Почему данные лежат именно там:

- книга, цена, наличие, выдачи → **SQLite/PostgreSQL**: нужны связи, ограничения целостности
  и транзакции (выдача книги меняет остаток);
- история поиска и счётчики → **Redis**: данные временные, часто перезаписываются, TTL
  удаляет их автоматически;
- обложки → **CDN**: большие неизменяемые файлы, которые выгодно кэшировать ближе к клиенту.

## 13. Вывод

В ходе работы REST-приложение из ЛР №10 переведено с хранения в `list` на реляционную БД:
спроектирована схема из пяти таблиц в 3НФ со связями 1:N и N:M, написаны DDL, тестовые данные

Дополнительно показано, что БД — не единственное место хранения: история поиска вынесена
в Redis (cache-aside, TTL, инвалидация при изменении данных), а обложки книг раздаются
через CDN-узел с `Cache-Control` и заголовком `Age`. Сравнение SQL, NoSQL, кэша и CDN
показывает, что выбор хранилища определяется характером данных: связи и целостность — БД,
временные данные — кэш, неизменяемая статика — CDN.
